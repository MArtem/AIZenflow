# Два слоя iOS-помощника: база знаний → библиотека

Статус: этап A завершён с оговорками 2026-09-29; B/C не начаты. «База знаний» — существующие активные локальные правила,
промпты, стандарты, навыки и знания. «Библиотека» — будущий copy-only слой,
сейчас расположенный в неактивном `reference-copy-only/`. Эти имена описывают
роль, а не разрешают переименовывать каталоги или менять загрузку Codex.

## Контракт и границы

- Это **эшелонированная защита**, а не два независимых продукта: на каждом
  применимом этапе инструкции проекта и база знаний дают первичное решение,
  затем библиотека независимо проверяет его на пропуски, слабые доказательства
  и риски. Найденное возвращается в тот же этап для исправления и повторной
  проверки. Конфликт не разрешается тихим переопределением первого слоя:
  записать обе нормы и факты, сохранить более высокий приоритет локальных
  правил и остановить готовность до разрешения существенного противоречия.
- `OFF`: полный локальный рабочий цикл и честная проверка итогового diff.
  `ON/AUTO`: тот же цикл плюс уместные библиотечные проверки в текущем
  разрешённом задании. `ON/ADVISORY`: аргументированные советы о целесообразности
  проверок и действий. Ни один режим сам по себе не разрешает сборку, тесты,
  агентов, Git, сеть, установку или изменение Codex.
- Текущая библиотека неактивна. Старые исходники, навыки и инструменты
  сохраняются до явного учёта их полезного содержания; неактивный архив нельзя
  считать готовым исполняемым payload. История Git остаётся без переписывания.
- Область первого аудита: общие действующие entrypoints, маршруты, iOS-стандарты,
  промпты, локальные iOS-навыки, общие знания и их проектные зеркала. App-specific
  решения проверяются на корректную изоляцию и ссылки, но не пересматриваются
  массово как продуктовые требования каждого приложения.

## Этап A — полное ревью базы знаний (сначала)

### Исполнение этапа A: шесть проверяемых итераций

Выбор пользователя для всего этапа A: **GPT-6 Sol, режим `эконом`**. Внутри
итерации — read-only обследование, реестр находок с доказательствами, затем
отдельные тематические исправления по 2–3 исходным документам с проверкой
потребителей и полного diff. Не объявлять завершение этапа по одному grep,
линеру, старому PASS или выборке из архива. Активность файла доказывается
точкой входа/маршрутом; история и неактивная copy-only библиотека не входят
в обязательный корпус первого слоя. Противоречия P0–P2 блокируют A6.

- [x] **A-I1 — inventory и authority (A0/A1):** зафиксировать canonical SHA,
  root/вложенные AGENTS, bootstrap/fallback, Level 0, registry/overlay, активные
  и исторические границы; построить трассы для старого и шаблонного нового
  проекта. Результат: воспроизводимая карта загрузки, неизвестное отдельно.
- [x] **A-I2 — маршруты и стоимость контекста (A1/A2):** проверить все машинные
  task routes, prompt/skill discovery и зеркала; различать обязательные,
  optional и trigger-only файлы, отсутствующие ссылки, циклы, повторы и
  неявную загрузку корпуса. Результат: матрица route → документы/владелец/
  риск/стоимость, точечные исправления подтверждённых дефектов.
- [x] **A-I3 — общая authority и риск-стандарты (A2–A4):** семантически
  проверить разрешения, модель, источник истины, evidence/readiness,
  секреты/privacy, Git/build/test authority, failure-closed и границы
  app-neutral/app-specific. Результат: finding ID для каждого дефекта,
  исправленные P0–P2 и явный остаток P3.
- [x] **A-I4 — iOS-семейства, промпты и навыки (A2–A4):** проверить покрытие и
  согласованность активных iOS-доменов, включая Swift/SwiftUI, concurrency,
  сеть, данные, архитектуру, ресурсы/локализацию, доступность, build graph,
  release и Figma→iOS. Проверить условия навыков и зеркала; не переписывать
  семейство только из-за одинаковых слов. Результат: покрытие каждого
  активного семейства и тематические правки с семантическим review.
- [x] **A-I5 — сценарии и негативные случаи (A5):** на фиксированных старом
  и шаблонном новом проекте трассировать review/fix/feature, разрешения,
  недостаток данных, конфликт правил, target/package/resource changes и
  перечисленные в A5 iOS-сценарии. Разделить статическую симуляцию и реально
  наблюдённую загрузку нового чата; не выдавать первую за вторую. Результат:
  вход → загруженный маршрут → решение → evidence/UNKNOWN → стоимость.
- [x] **A-I6 — окончательный gate (A3/A4/A6):** проверить учёт всех findings,
  отсутствие нерешённых P0–P2, статические индексы/границы/зеркала, полный
  итоговый diff и затронутые утверждения; перепроверить после исправлений.
  P3 либо устранены, либо названы с воздействием. Результат: точный отчёт
  «готово/не готово» и перечень неполученного runtime/new-chat evidence.

Не переходить к B до A-I6. Канонический документационный репозиторий
публикуется после его gate по действующему разрешению; проектные коммиты и
пуши в AIZenflow требуют отдельного явного разрешения и безопасного переноса
без слияния старой ветки с историей установщика. Ни одна итерация не меняет
Codex host, установщики, auth или Keychain.

- [x] A0. Зафиксировать точный inventory/версию: канонический checkout,
  активные источники, зеркала, маршруты, индексы, владельцев, архивы и точки
  входа. Отдельно пометить «активно», «по триггеру», «архив», «неизвестно».
  Никакой файл не получает статус активного только из-за нахождения в каталоге.
- [x] A1. Построить граф загрузки от `AGENTS.md`/bootstrap до Level 0,
  task routes, промптов и навыков для типовых старого и нового iOS-проекта.
  Проверить отсутствие циклов, несуществующих ссылок, неправильного приоритета,
  недоступных обязательных документов, неявного полного чтения корпуса и
  противоречий между canonical source и зеркалами.
- [x] A2. Провести инвентаризацию качества каждого активного семейства:
  фактическая применимость к современному iOS/Swift/Xcode, чёткость условий,
  authority/permission, проверяемость, актуальность, app-neutral граница,
  своевременное сообщение о недостатке доказательств. Классифицировать
  ошибки, двусмысленности, противоречия, дубли, утраты контекста и пропуски.
  Проверять содержание, не полагаться лишь на grep или линтер.
- [x] A3. Для каждой находки записать ID, источник и потребителей, цитату
  или точный диапазон, риск и сценарий ошибки, приоритет P0–P3, рекомендуемый
  единый источник истины, минимальную правку и способ доказать исправление.
  P0–P2 устранять до объявления первого слоя качественно готовым; P3
  исправлять либо явно заносить в остаточный список.
- [x] A4. Исправлять по небольшим тематическим блокам (обычно 2–3 документа):
  сначала authority/bootstrap/маршрутизация, затем общие стандарты, затем
  iOS-домены, промпты/навыки и зеркала. Перед правкой — contract и список
  потребителей; после — точечная проверка, полный diff и повторный взгляд
  на смысл. Не делать массовых механических переписываний без выборочной
  семантической проверки.
- [x] A5. Провести сценарную проверку первого слоя: новый/старый проект,
  review, fix, feature, архитектура, concurrency, persistence, build graph,
  ресурсы/локализация, Figma→iOS, no-build permission, недостаток данных и
  конфликт проектного исключения с общей базой. Зафиксировать фактический
  набор загруженных документов, решение и честность доказательств.
- [x] A6. Gate базы знаний: нет нерешённых P0–P2, основные маршруты и зеркала
  непротиворечивы, статические индексы/границы проходят, сценарии задокументированы,
  изменения проверены по полному diff. Только после этого использовать слой
  как стабильную опору для оценки библиотеки. Непроверенное пометить явно.

Итог A: **READY_WITH_LIMITATIONS для первого слоя как документальной опоры**,
не сертификат production-качества iOS-кода. Наблюдена загрузка startup/Level 0
в новом чате; выбор всех specialist skills, фактические build/runtime-пути и
каждый внешний API-тезис не подтверждены. Остаток P3/UNKNOWN — в audit ledger.

## Этап B — полное внедрение и ревью библиотеки

- [ ] B0. Сопоставить весь сохранённый V5.4-корпус с полезными функциями:
  документы, все бывшие `ioslib-*` навыки, аудиты, рекомендации, агентные
  маршруты, шаблоны и четыре сохранённых скрипта. Для каждого — активный
  copy-only маршрут, безопасное преобразование, архивный источник или
  обоснованное исключение. Не обещать функциональной эквивалентности старому CLI.
- [ ] B1. Спроектировать минимальный переносимый payload и его точный allowlist.
  Отделить самодостаточные правила от исходных снимков; устранить установочные
  команды и зависимости от runtime/config.toml/auth/Keychain. Проверить пути,
  ссылки, инструкции и побочные эффекты. Уникальное окончательное имя выбрать
  перед публикацией, без преждевременного переименования действующих путей.
- [ ] B2. Довести управление отдельным Xcode-проектом: `UNSET/OFF/ON`,
  видимый статус, явное решение при UNSET, `AUTO/ADVISORY`, безопасная смена

  управления. Состояние не должно зависеть от установки в Codex; неизвестное
  или неоднозначное значение означает OFF до решения пользователя.
- [ ] B3. Довести библиотечные маршруты для каждого типа работы: диагностика,

  ресурсы/локализация, дизайн→iOS, полный аудит проекта, выборочный аудит,
  pre-PR diff и координация агентов. Первым всегда проходит соответствующий
  маршрут базы знаний; библиотечный findings pass не подменяет его.
- [ ] B4. Портировать только доказанно нужные read-only инструменты после
  независимой проверки зависимостей, входов, выходов и fail-closed ошибок.
  Убрать зависимость сканера от старого runtime и подавление ошибок в
  `verify_diff.sh`; не запускать сохранённые исходники как готовый продукт.
- [ ] B5. Оценить OFF/ON/AUTO/ADVISORY на одном наборе фиксированных задач:
  полнота находок, ложные срабатывания, уместность рекомендаций, отсутствие
  конфликта с локальными правилами, стоимость контекста, честность PASS/UNKNOWN
  и качество итогового diff. Проводить без установки и без изменений
  пользовательских проектов; runtime-сборки/тесты — только по разрешению.
- [ ] B6. Независимое итоговое ревью точного payload, каждого активного
  навыка/команды, ссылок, границ прав, совместимости с базой знаний и полного
  diff. P0–P2 блокируют готовность. После исправлений повторить итоговый
  обзор, получить явное разрешение на пилотное копирование в **один** проект,
  затем проверить новый чат, ON/OFF и откат без изменения инфраструктуры Codex.

## Этап C — совместная работа слоёв

- [ ] C0. На одинаковых сценариях прогнать трассу: локальные правила/база
  знаний → решение и доказательства → библиотечный второй проход → исправление
  → повторная проверка → единый итоговый diff. Проверять это для планирования,
  ревью, генерации кода/ресурсов, тестовой стратегии и pre-PR состояния.
- [ ] C1. Измерить добавочную пользу второго слоя: какие реальные ошибки он
  нашёл после первого, какие пропустил оба, какие создал ложные замечания,
  сколько возникло дублированной работы и где выросла стоимость контекста.
  Общий PASS недопустим, если один обязательный слой не выполнился.
- [ ] C2. Проверить конфликты authority и отказоустойчивость: библиотека не
  ослабляет локальный запрет; недоступный/непонятный второй слой явно даёт
  `INSUFFICIENT_EVIDENCE`, а не ложный PASS; OFF сохраняет полный первый слой;
  ON не запускает запрещённые действия. Существенный конфликт блокирует
  готовность и создаёт точечную задачу на исправление источника нормы.
- [ ] C3. Финальный gate пары: на репрезентативных старом и новом iOS-проекте
  подтверждены порядок, покрытие, честность доказательств, разрешение
  конфликтов и добавочная польза. Только после этого предлагать результат
  пользователю как прошедший оба слоя; непроверенные runtime/visual/device
  проверки отмечать отдельно.

## Порядок работы и публикации

Первый рабочий блок — A0/A1: read-only inventory и граф реальной загрузки.
Затем выдаётся реестр находок с приоритетами; правки идут малыми блоками.
Сначала завершается gate A, затем B0–B6 и обязательно C0–C3. Каждая публикация в Git требует
проверки итогового diff и remote SHA; активные планы `main`/`development`
нельзя перекрывать планом текущей рабочей ветки. Настройки Codex,
установщики, auth и Keychain вне области этой работы.
