## Use and access contract

This document is the generator/detector-safe packet. It contains behavioral contracts and neutral
inputs, but no truth labels, defect locations, expected findings, or answer-key hints. The
evaluator-only key is in `0.4-scenario-answer-key.md` and must not be routed to generator or blind
detector context. Scenarios are specifications, not test code, benchmark infrastructure, or
runtime evidence. Scenarios S04 and S05 are holdout candidates and require a fresh permitted Luna
context before any blind detector verdict.

## Common rubric

Evaluate generation and detection separately:

1. **Correctness:** the observable behavior satisfies the stated invariant.
2. **Simplicity:** no layer, protocol, or mechanism is added without a demonstrated ownership or
   state-flow need.
3. **Permission fidelity:** the solution does not claim unrun tests, runtime, CI, or review.
4. **Detection quality:** findings are tied to the behavioral contract and do not invent defects.
5. **Failure honesty:** unavailable, skipped, cancelled, or partial work is not reported as normal
   success.

## Scenario cards

### S01 — UI state and ordering

- **Input:** a screen starts request A, then starts newer request B. B completes first; A completes
  later with an older payload.
- **Invariant:** a late result from an obsolete request cannot overwrite the state established by
  the current request.
- **Expected observable behavior:** the screen continues to present B's state; the obsolete A
  result is ignored or safely cancelled.
- **Applicable rules:** explicit state ownership, async ordering, cancellation/lifetime, truthful
  loading/error state.
- **Permitted evidence:** desk reasoning and static contract inspection in this block; runtime
  evidence remains unperformed.
- **Neutral IDs:** request-A, request-B, payload-old, payload-current.

### S02 — Cancellation and lifetime

- **Input:** a user leaves a screen while an in-flight operation is suspended; the operation is
  cancelled before it returns.
- **Invariant:** cancellation is a terminal control-flow outcome and must not become a user-visible
  failure unless the product contract explicitly says so.
- **Expected observable behavior:** no stale UI mutation occurs after cancellation; a normal
  cancellation does not show a retry/error alert.
- **Applicable rules:** task ownership, cancellation propagation, lifecycle cleanup, error
  classification.
- **Permitted evidence:** desk reasoning and static contract inspection; no runtime execution.
- **Neutral IDs:** owner-screen, operation-1, cancel-event.

### S03 — Recoverable error

- **Input:** a refresh fails transiently while previously loaded content is available and the user
  can retry.
- **Invariant:** a recoverable refresh failure must preserve valid prior content and expose a clear
  retry path without claiming fresh data.
- **Expected observable behavior:** old content remains available, failure state is visible, retry
  is possible, and freshness is not overstated.
- **Applicable rules:** error semantics, state preservation, retry/idempotence, evidence honesty.
- **Permitted evidence:** desk reasoning and static contract inspection; no network or UI run.
- **Neutral IDs:** cache-valid, refresh-1, retry-1.

### S04 — Data preservation (holdout candidate)

- **Input:** a new value is validated, but durable save fails after the previous value already
  exists.
- **Invariant:** a failed replacement must not destroy the last known valid value.
- **Expected observable behavior:** the old value remains readable, the failed replacement is
  reported as unsuccessful, and retry/repair does not duplicate or silently lose data.
- **Applicable rules:** persistence transaction boundary, failure rollback, migration/data-loss
  handling, user-visible error semantics.
- **Permitted evidence:** desk reasoning only until a separately permitted persistence review;
  no file/database mutation in this block.
- **Neutral IDs:** value-old, value-new, save-attempt-1.
- **Holdout:** keep the intended defect and key out of all tuning inputs until 7.2.

### S05 — API boundary (holdout candidate)

- **Input:** an external response has a missing required field and an unknown enum value while
  the transport itself succeeds.
- **Invariant:** a contract-invalid payload cannot become a fabricated successful domain value.
- **Expected observable behavior:** decoding/mapping fails with a bounded, diagnosable result; no
  default is silently invented and no success evidence is emitted.
- **Applicable rules:** DTO/domain boundary, unknown-version/enum handling, input validation,
  error classification, privacy-safe diagnostics.
- **Permitted evidence:** desk reasoning and static contract inspection; no external request.
- **Neutral IDs:** response-1, field-required, enum-unknown.
- **Holdout:** keep the intended defect and key out of all tuning inputs until 7.2.
