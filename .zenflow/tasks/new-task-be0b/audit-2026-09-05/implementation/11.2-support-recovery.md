## Contract and limits

Support is trigger-based and bounded. It does not create a scheduler, background monitor, hook,
telemetry service, or recurring full audit. Every response uses Luna xhigh, the current selected
specialist route, and a fresh receipt when a source identity or contract changes. Existing evidence
is reusable only when source, policy, profile, permission, and artifact identities still match.

## Review triggers

| Trigger | First action | Required evidence | Stop/owner |
| --- | --- | --- | --- |
| Swift, Xcode, SDK, Apple API, or provider contract changes | Record the new version/date and select the affected specialist route | Primary source, compatibility impact, changed rule/profile/adapter identities | Stop before adoption if availability or semantics are uncertain |
| QC engine, schema, catalog, profile, or consumer pin changes | Freeze stable promotion and compare exact old/new identities | Diff, schema compatibility, catalog maturity, consumer impact, rollback pin | Engine owner plus affected consumer owner |
| Missed P1/P2, false PASS, or evidence forged/stale | Preserve the failing artifact and mark the prior verdict non-promotable | Reproduction or bounded static trace, exact source/engine/profile SHA, severity and scope | P0–P2 blocks commit/push/promotion until fixed or explicitly accepted by the proper authority |
| Repeated false positive or unnecessary route/read | Classify the specific rule and inspect its producer/consumer contract | Representative benign case, selected route, correction, regression guard | Do not weaken a global floor from one example |
| Consumer target, localization, package ownership, or permission changes | Keep issue app-local and re-run only the affected pilot slice | Updated profile/manifest, ownership decision, static receipt | No global promotion from an app-specific fix |
| Receipt becomes stale or a required source is unavailable | Mark evidence stale/blocked; do not reuse it as PASS | Identity mismatch or unavailable source, remaining risk, next safe action | Recovery owner decides whether to re-run or defer |
| Future product starts requirements/design | Create a product-owned profile and app documentation boundary | Product contract, target/toolchain facts, exception/permission scope | Do not activate stable QC solely because preparation is ready |

## Recovery ladder

1. **Contain.** Stop promotion, release, or adoption at the narrowest affected boundary. Preserve
   the last verified receipt and the failing/blocked artifact; do not delete evidence or relabel a
   bypass as `PASS`.
2. **Identify.** Compare exact source, engine, schema, profile, toolchain, permission, and artifact
   identities. Classify the state as `FAIL`, `BLOCKED`, `NOT_RUN_BY_USER_DECISION`, stale, or an
   ordinary documentation defect.
3. **Route.** Read Level 0, task state, and only the changed specialist route. Use the broad route
   only for a cross-cutting authority or semantic conflict. Reuse unchanged evidence only after
   identity binding succeeds.
4. **Correct.** Make one self-contained patch under the compact change contract. Keep reusable
   policy in Documentation Vault, engine/schema/adapters in QualityControl, and app facts or local
   exceptions in the owning consumer.
5. **Verify.** Run the permitted static check or owner-authorized runtime check. Review the complete
   final diff, affected call sites, mirrored claims, false-success paths, resource limits, and
   irreversible state. P0–P2 findings block commit and push.
6. **Recover or defer.** If the correction is valid, publish a new receipt with new identities and
   update only the affected consumer. If evidence is unavailable or the product decision is open,
   retain the blocker and record `deferred`/`NOT_READY` with a concrete next action.

## Rollback anchors

- QualityControl last verified pin: `b197bd5e8983b5c7cfd1d277dd2540d7bb352a15`; return the
  consumer to this compatible release/profile pair when a new engine revision is rejected.
- Documentation Vault rollback: revert the exact canonical commit that changed the rule, then
  refresh generated mirrors through the single generator; do not hand-edit a mirror to hide drift.
- Consumer rollback: restore the prior tracked profile/workflow pin and retain the failed receipt;
  do not rewrite history or delete the app-local blocker.
- Task-state rollback: preserve the current `plan.md`/`handoff.md` and add a bounded recovery
  receipt; move superseded detail to task history rather than expanding Level 0.

## Maintenance record

Each support action records: trigger, date/source revision, affected route and owner, exact before
and after identities, decision, evidence status, checks run, omitted/denied checks, residual risk,
rollback anchor, and revisit condition. Usage and elapsed time remain `unknown` when unavailable.
The record is compact and task-local; no raw logs, source, secrets, or telemetry stream is added.

## Decision

**PASS_WITH_LIMITATION for lightweight support and recovery.** The system now has explicit triggers,
containment, identity-bound evidence reuse, targeted correction, rollback anchors, and a recovery
record without speculative automation. This does not close 8.2, 9.1, or 9.2 and does not activate
stable release or future-product adoption.

## Invalidation

Revisit this contract when release/source ownership, QC evidence schemas, model routing, consumer
boundaries, or user permissions change. A new product or a repeated P0–P2 should open a new bounded
implementation block rather than silently expanding support into a permanent full audit.
