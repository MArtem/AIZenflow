## Change contract

- Reusable package docs own neutral capability, boundary, revision and verification contract.
- `PackagesForReuse` is a reviewed source snapshot; `PackagesInUse` and target membership are
  consuming-app integration state.
- Adoption, migration, rollout and rollback history belongs under `apps/<AppName>/` or the task;
  reusable catalogs do not silently claim that a package is active in an app.
- The historical 50-iteration SDK roadmap is reference data and cannot create an automatic next
  package or release claim.
- Verification examples identify output/build/cache roots, package revision and permission state;
  reading an instruction does not authorize executing a permission-sensitive command.

  explicit classification/redaction because path or slug is not safe by default.

## Acceptance scenarios

1. A new project can select a package capability without inheriting Tchop/source-app target
   membership, product policy or rollback history.
2. An app adoption receipt can identify package path, content/repository revision or published tag,
   Documentation Vault revision, target scope, verification evidence and rollback path.
3. The 50-iteration roadmap and status matrix do not force the next numbered package or imply
   release readiness.
4. A package verification template names output/build/cache roots and records skipped/denied/
   unavailable permission-sensitive execution honestly.
5. Package privacy guidance rejects the assumption that removing URL query/fragment also removes
   account identifiers or private slugs.
