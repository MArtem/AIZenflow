## Implemented changes

- Replaced comment-only masking with a bounded Swift lexical adapter covering nested block comments,
  normal/raw/multiline strings, escaped characters, and interpolation. Code inside `\(...)` and
  raw-string interpolation remains searchable; literal text is masked while line positions survive.
- Changed static disabled-test matching to operate on masked source and added conservative
  `#if`/platform-scope labels. The report no longer claims that every `XCTSkip` is unconditionally
  executed or that static source proves runtime selection/execution.
- Made malformed lexical structure fail closed through `AdapterError`/`BLOCKED` and capped lexer
  nesting. No new parser dependency was introduced.
- Reworded the hot-path catalog, remediation, reports, README, policy README, and fixture contract
  to make the policy-ban authority explicit and remove executor/runtime overclaiming.
- Kept all test sources untouched. The fixture README records positive/negative lexical cases and
  the boundary for `withKnownIssue`, `XCTSkipIf/Unless`, target membership, and runtime counts.

## Acceptance mapping

- A token in a line/block comment, ordinary string, raw string, or multiline string is not reported.
- A token in string interpolation is reported as code.
- Nested comments and nested strings inside interpolation remain masked correctly.
- Unterminated string/comment/interpolation is `BLOCKED`, never a normal `PASS`.
- A disabled attribute or `XCTSkip(...)` in a `#if`/`#if os(...)` region is labeled as conditional or
  platform-gated context; lack of a preprocessor gate is not treated as proof of runtime execution.
- `withKnownIssue`, `XCTSkipIf/Unless`, target membership, and selected/executed test counts stay
  outside this static check and are explicitly named as separate evidence.
- Hot-path findings use policy-removal language rather than promising that an async wrapper proves
  executor isolation or runtime performance.
