## 1. Цель, смысл «максимально» и границы результата

**Цель:** максимально повысить качество и эффективность всей связки в реальной разработке на выбранной модели. База знаний, Library, проектная память, маршрутизация и способы проверки рассматриваются как одна система. Улучшение отдельного слоя ценно настолько, насколько оно улучшает итоговую работу.

Приоритеты, по порядку:

1. Корректный результат и соблюдение реальных пользовательских требований/полномочий.
2. Меньше существенных ошибок, пропусков, ложных замечаний, регрессий и переделок.
3. Более устойчивый результат на разных задачах и проектах.
4. Меньше времени, контекста, лишних действий и вмешательств пользователя при сопоставимом качестве.
5. Разумная стоимость поддержки самой системы.

«Максимально» означает последовательное устранение доказанных ограничений и выбор лучшего проверенного варианта в согласованном бюджете. Конечная серия экспериментов не доказывает математический глобальный оптимум. В отчёте указываются достигнутые улучшения, оставшиеся ограничения и следующая наиболее ценная возможность.

Количество документов, слов, правил, маршрутов, агентов, тестов и отчётов не является показателем успеха. Сокращение полезной обязательной проверки ради скорости также не является улучшением.

Разрешённые направления дизайна: дополнение знаний, исправление ошибок, углубление примеров, объединение/разделение материалов, изменение границ KB/Library, улучшение поиска и доставки, проверенные диагностические рецепты, проектная память, преобразование повторяющегося объективного правила в небольшой проверяющий инструмент. Каждое направление проходит проверку необходимости и своего фактического эффекта.

## 3. Организация исполнения и полномочия

### 3.1 Модель и размер блоков

- Реализатор и основные экспериментальные исполнители: **GPT-6.1 Sol, reasoning medium**. Не подменять эту конфигурацию более сильной внутри сравнения.

## 5. Единый контракт проверки и приёмки

### 5.1 Статусы

- `NOT_STARTED`, `IN_PROGRESS`, `READY_FOR_REVIEW` — состояния работы.
- `ACCEPTED_STATIC` — подтверждена только объявленная статическая часть; не означает runtime-правильности или пользы.
- `ACCEPTED_SCOPED` — выполнены все критерии конкретного пункта в указанной области.
- `REJECTED` — критерий не выполнен с достаточными доказательствами.
- `INCONCLUSIVE` — данных или устойчивости недостаточно; это не PASS и не доказательство бесполезности.
- `BLOCKED` — необходимая зависимость/разрешение/среда отсутствует; причина и следующий конкретный шаг записаны.
- `N/A` — доказанная неприменимость; `OMITTED_BY_USER` — явное исключение пользователя. Ни один из них не засчитывается успехом.

Действующий общий словарь severity/evidence имеет приоритет. Эти task-статусы не заменяют его.

### 5.2 Карточка результата каждого Pn.m

ID и R-ID → гипотеза/пользовательский результат → входные SHA/источники → разрешения → изменённые артефакты → фактическая проверка и её результат → находки → критерий принятия → расход/UNKNOWN → drift-check → решение/следующий шаг.

Достаточно одной компактной записи и ссылок на исходные доказательства. Не создавать отдельный большой отчёт для каждой команды. При изменении входа переиспользовать только доказательства, зависимость которых не изменилась.

### 5.3 Измерения

| Метрика | Как считать | Ограничение |
|---|---|---|
| Task success | Выполнены все заранее определённые обязательные требования и применимые проверки | Один прошедший тест либо убедительный текст ответа недостаточен |
| First-pass success | Первый завершённый кандидат принят без исправляющей итерации | Не скрывать промежуточные откаты и подсказки |
| Ошибки результата | Подтверждённые correctness/regression findings по общей severity | Отличать дефект, гипотезу и предпочтение стиля |
| Точность ревью | TP/(TP+FP), с отдельными disputed/unverified | При нулевом знаменателе N/A; unknown не считать FP или TP автоматически |
| Полнота ревью | Найденные известные ошибки / полный известный набор | Recall допустим только для случая с достоверным oracle; в открытом проекте полный recall UNKNOWN |
| Переделки | Число необходимых исправляющих итераций и причина каждой | Размер diff/число строк — диагностический признак, не оценка качества |
| Время | End-to-end wall time до принятого результата, отдельно ожидания/подготовка | Сравнивать одинаковые границы; показать медианы, разброс и выбросы |
| Расход | Доступные input/output/cached tokens и другие реально наблюдаемые единицы | Не переводить подписку в выдуманную цену; отсутствие данных = UNKNOWN |
| Участие пользователя | Число и тип вмешательств, необходимых для завершения | Обязательное получение полномочий не штрафовать как плохую инициативу |
| Доставка | Правильный материал выбран, получен до решения и корректно применён | Само упоминание пути или самоотчёт о прочтении недостаточны |
| Контекст | Фактически загруженный объём и повторные чтения | Размер всего корпуса и верхняя граница route не равны фактическому расходу |
| Поддержка | Работа на обновление, исправление drift и повторную валидацию | Учитывать отдельно от стоимости единичной задачи |

Приоритет сравнения: полномочия/безопасность → task success → существенные дефекты/ложные замечания/переделки → время и расход. Не сворачивать всё в удобный средний балл, маскирующий ухудшение важного свойства.

### 5.4 Протокол сравнения

**A:** текущая связка на зафиксированных версиях. **C:** улучшенная связка целиком. Это основное сравнение.
**B:** улучшенная KB без нового прикладного модуля — необязательная диагностическая абляция, только если она помогает выбрать конкретное изменение. Отсутствие отдельного выигрыша C над B не отменяет полезный выигрыш всей системы C над A.

Для A/C одинаковы: GPT-6.1 Sol/medium, задача, исходный commit, рабочие данные, разрешённые инструменты, итоговая рубрика, аппаратная среда где применимо, лимиты и возможность повторной проверки. Вариант C не получает дополнительный скрытый review-бюджет. Порядок A/C чередуется/рандомизируется до запуска и записывается.

Сохраняется общая высшая цепочка полномочий и безопасности. Экспериментальный knowledge payload выбирается явно и имеет hash. Живые канонические ссылки не должны незаметно переключать A на новую версию C. Изменение общих обязательных правил во время серии останавливает сравнение: фиксируется новый baseline либо оформляется отдельное допустимое экспериментальное разделение без ослабления правил.

Каждая попытка стартует в свежем изолированном контексте и чистом независимом состоянии проекта. Без результатов другой попытки, предыдущих патчей, ответов oracle или персистентной памяти, способной раскрыть решение. Shared caches допустимы только при симметричном, записанном использовании. Идентичные запреты и условия доступа применяются к обеим сторонам.

Оценивание начинается с результата/изменённого состояния и объективных проверок. Оценщик получает анонимизированные артефакты без метки A/C. Модельный judge помогает применять рубрику, но его уверенность не заменяет тест/контракт/трассу. Спорные значимые случаи требуют отдельного разбора; при отсутствии разрешённой независимой проверки соответствующий вывод ограничивается и не называется независимым.

**Неуспех доставки Library входит в основной результат C.** Его нельзя исключить как «невалидный», потому что файл не прочитан. Дополнительный диагностический запуск с явно переданным материалом маркируется отдельно и не подменяет основной outcome. Исключения из анализа разрешены только по заранее заданным внешним причинам, симметричным для A/C; все исключённые и незавершённые попытки остаются в журнале. Ошибка подготовки самой системы — её результат, а не удобное исключение.

### 5.5 Набор задач и объём

Предложенный полный объём; он станет рабочим только после P2 и оценки бюджета:

- Countries, Ghibli, Firefox — три кандидата. Проверить реальные пути, технологии, возможность воспроизведения и лицензионные условия. Не выдумывать в них дефекты. Если проект не даёт пригодного случая, обосновать замену до заморозки набора.
- **12 development-задач:** 4 на проект; смесь review, bug fix и небольшого изменения/рефакторинга. Не менее трёх clean/negative-control случаев, где лишнее исправление ошибочно. Исторические задачи допустимы здесь.
- **12 независимых holdout-задач:** 4 на проект, сходное распределение классов, без копий development-дефектов и без раскрытия решений автору материалов. Каждый использованный holdout после раскрытия переводится в development.
- Отдельно от coding-набора — 12 коротких route-вопросов, включая четыре нерелевантных/неоднозначных/устаревших случая. Они проверяют доставку и не добавляются к числу успешных продуктовых задач.

| Серия | Объём | Назначение |
|---|---:|---|
| Доставка/среда | 4 репрезентативных сценария × A/C = 8 попыток | Доказать работоспособность механизма, откалибровать стоимость |
| Development | 12 задач × A/C × 1 = 24 попытки | Найти полезные изменения и слабые места, без финального статистического вывода |
| Holdout | 12 задач × A/C × 3 = 72 попытки | Основная проверка повторяемости на неизвестных задачах |
| Прикладное внедрение | 3 новые задачи × A/C × 1 = 6 попыток | Проверить работу вне специально подготовленной серии |
| Диагностический B | До 6 дополнительных попыток по отдельному вопросу | Разобрать причинный вклад; не обязательный ритуал |

Основной план — **110 попыток**, если все этапы потребуются и будут разрешены; диагностические прогоны и корректирующие повторы учитываются дополнительно и не запускаются автоматически. Одна попытка не обязательно равна отдельному видимому чату: важна реальная изоляция, которую P2 проверяет. Десятки свежих контекстов требуют согласованного способа запуска; вручную имитировать независимость в одном длинном чате нельзя.

Число 110 — оценка запланированного объёма, не разрешение потратить этот бюджет. После первых восьми попыток оценить время/расход следующей серии с диапазоном неопределённости. Если полный объём не принят, выбрать меньший протокол заранее и сузить силу итогового утверждения. Не объявлять две удачные задачи эквивалентом полного gate.

### 5.6 Предлагаемые пороги итоговой приёмки

Пороги ниже — проектное предложение, а не статистический закон. P2 фиксирует их до holdout; после просмотра результатов менять их для получения PASS запрещено.

Обязательные условия:

1. Полный журнал всех предусмотренных попыток, входные версии и разделение development/holdout восстановимы.
2. Ноль нарушений полномочий/секретной границы/сохранности чужих данных. Ноль известных неустранённых P0–P2 в выпускаемых материалах и механизме; подтверждённая P0–P2 регрессия, вызванная системой, блокирует её выпуск.
3. C принимает задачу в большинстве повторов (не менее 2 из 3) минимум в 10 из 12 holdout-задач; это рабочий порог области пригодности, не обещание универсальности.
4. Принятый вариант показывает практически значимый эффект по одному из путей ниже, минимум на двух проектах и двух типах задач. Нельзя компенсировать провал одного проекта успехом другого и заявить одинаковую пригодность для обоих.

**Путь Q — преимущество качества:** число успешных попыток C как минимум на 4 из 36 выше A; число задач с преимуществом C по success rate больше числа задач с проигрышем минимум на 3. First-pass success, подтверждённые существенные ложные замечания и переделки отдельно не должны показывать скрытого систематического ухудшения. Повышенная стоимость допустима только как заранее согласованный trade-off качества; её измеряют и явно показывают.

**Путь E — преимущество эффективности:** success rate C не ниже A ни в одном заранее выделенном проектном срезе; значимых дефектов/ложных замечаний и необходимых переделок не больше; медианное парное время до принятого результата улучшено минимум на 20% и выигрыш виден минимум на двух проектах. Tokens, если доступны, не должны скрывать неприемлемый рост; при UNKNOWN можно заявлять выигрыш времени, но не экономию токенов/денег.

Разница в одну случайную попытку не становится доказательством. Для обоих путей показать парные результаты по всем задачам, распределение повторов и интервалы неопределённости с группировкой по задаче. 72 попытки — **12 парных задач**, а не 72 независимых наблюдения. Если выбранный до запуска способ анализа не позволяет отделить улучшение от шума, итог `INCONCLUSIVE`, даже при достижении численного порога. Расширение выборки — отдельное решение, без бесконечного добора до положительного результата.

Известный хороший результат A может дать потолочный эффект. Тогда заранее предусмотренный путь E остаётся допустимым. Декоративный новый rubric после получения равных результатов недопустим.

## 6. Порядок этапов

Зависимости: **P0 → P1 → P2 (дизайн протокола и бюджет разработки) → P3/P4 → P5 → P2.4 (фактическая калибровка и бюджет основной серии) → P6 → P7 → P8 → P9**. P2.4 закрывается после готовности доставки; это явный возврат к бюджетному gate, а не циклическая зависимость реализации.
P3 и P4 допускают независимые подблоки после фиксации единого контракта; это не разрешение создавать агентов. Сначала довести один сквозной модуль до проверяемого использования, затем расширять на другие. Holdout не используется для разработки.

Каждый пункт ниже наследует разделы 3, 5 и 8. Внутри пункта перечислены конкретный результат, проверка, критерий и действие при отклонении. Отсутствие требуемого доказательства оставляет пункт открытым.

### P0. Восстановить действительную исходную точку

**P0.1 — Scope, полномочия, идентичность и сохранность.**
- Результат: компактный реестр разрешений; фактические roots, selectors, ветки, SHA, dirty state; перечень затрагиваемых canonical/local материалов. Состояние предыдущего цикла сохранено отдельно.
- Проверка: canonical bootstrap → текущий router/Level 0 → task state → применимые routes/overlays; сопоставление с последними решениями пользователя. Read-only Git/worktree inspection без переключения занятых веток.
- Принятие: для каждого следующего действия известны authority, writable scope и исходный SHA; неизвестность отмечена явно; чужие изменения атрибутированы либо исключены из patch. Ни одно старое разовое разрешение не «восстановлено» предположением.
- При отклонении: блокировать только зависимое действие, запросить недостающий конкретный выбор; продолжить независимую разрешённую диагностику. Нельзя расширять scope ради удобства эксперимента.

**P0.2 — Зафиксировать baseline A и реестр доказательств.**
- Результат: версии действующей KB, Library, доставки и проектной памяти; карта реально активных входов и зеркал; ссылки на прошлые полные протоколы, включая неудачи.
- Проверка: выбрать по одному известному маршруту каждого активного входа и проследить фактический путь до источника. Перепроверить исторические missing/stale, не сканируя каждый файл без причины. SHA/хеши должны однозначно восстанавливать экспериментальный payload.
- Принятие: A воспроизводим без обращения к изменяемому будущему C; источник обязательных правил отделён от экспериментального содержимого. Исторические факты и нынешние измерения различимы.
- При отклонении: сначала восстановить идентичность baseline. Не объявлять новый baseline прежней системой и не использовать исправленный C в контрольной группе.

**P0.3 — Сформировать карту исходных проблем и границы измерения.**
- Результат: 5–10 наиболее дорогих наблюдавшихся сбоев: ожидание → фактический результат → последствия → доказательства → возможная причина → уверенность. Допустимо меньше, если фактов недостаточно.
- Проверка: перечитать исходный материал для каждого значимого вывода; различать содержание, доставку, исполнение, окружение и недостаточность самого эксперимента. Включить ложные замечания и лишнюю работу, а не только пропущенные дефекты.
- Принятие: каждая будущая приоритетная мера имеет хотя бы один подтверждённый дефицит либо явно обозначенную проверяемую гипотезу. Нет выдуманных частот или стоимости.
- При отклонении: UNKNOWN сохраняется; назначить дешёвую диагностическую проверку. Не писать правило по одному непонятому инциденту.

**Gate P0:** безопасный scope и воспроизводимая отправная точка готовы. Это разрешает проектирование, но не доказывает пользу системы.

### P1. Найти ограничения и выбрать целевое устройство

**P1.1 — Аудит полезности содержимого и дублирования.**
- Результат: карта «оставить / уточнить / объединить / перенести / архивировать / добавить» для материалов, затронутых выбранными проблемами; владелец каждой нормы и факта.
- Проверка: сравнить не только формулировки, но и authority, применимость, конкретность примеров, версии платформы и потребителей. Подготовить предварительные 12 диагностических запросов, которые P2.1 окончательно зафиксирует, и пройти их до изменений; фиксировать найденное, пропущенное и нерелевантное.
- Принятие: у каждого предлагаемого удаления/переноса известен заменяющий источник и список входящих ссылок; полезная уникальная информация сохраняется. У каждого дополнения есть потребитель и ситуация применения.
- При отклонении: спорные материалы остаются с пометкой; массовая чистка по сходству текста не допускается. Количество удалённых слов не является успехом.

**P1.2 — Сравнить значимые варианты.**
- Результат: таблица минимум трёх вариантов: (A) точечные улучшения текущей структуры; (B) тонкое нормативное ядро + практические модули + адресная доставка; (C) расширенный индекс/поиск или небольшой проверяющий инструмент при доказанном ограничении. Для каждого — ожидаемый эффект, миграция, maintenance, риски, обратимость, стоимость/UNKNOWN.
- Проверка: пройти на бумаге два конкретных сценария из P0: что получает Sol/medium, когда, сколько действий требуется, как неверное знание обнаруживается. Более сложный вариант должен устранять ограничение, оставшееся у простого.
- Принятие: пользователь выбирает значимый подход после конкретного сравнения. Рекомендуемый старт — B без новой инфраструктуры поиска: он позволяет проверять содержимое и доставку отдельно. C выбирается только при фактической потребности.
- При отклонении: не строить платформу «на будущее». Дешёвая необратимость не считается преимуществом; при сопоставимом эффекте выбрать меньшую сложность.

**P1.3 — Зафиксировать контракты слоёв и приоритетный backlog.**
- Результат: одностраничная схема владельцев, source of truth, потребителей, жизненного цикла и допустимых зависимостей; очередь из 3–5 тем первого цикла с ожидаемым механизмом пользы и способом проверки.
- Проверка: каждая тема связана с P0/P1.1, поддерживается выбранными проектами и не требует скрытого продуктового решения. У каждой нормы один authoritative owner; Library ссылается на него, не переопределяет полномочия.
- Принятие: выбраны один сквозной модуль и максимум четыре следующих. Предварительные кандидаты: cancellation/lifetime; persistence/migration/rollback; media/cache/resource limits; ошибки/retry/offline; сохранность рабочего состояния. Окончательный состав определяется фактами, а не этим перечнем.
- При отклонении: тему без измеряемого потребителя оставить в backlog. Расширение за пределы пяти тем требует доказанной новой потребности и отдельного бюджета.

**Gate P1:** согласован механизм улучшения, а не только список документов. Технический выбор и значимые trade-offs показаны пользователю.

### P2. Подготовить честную и конечную проверку

**P2.1 — Выбрать задачи и диагностические запросы.**
- Результат: реестр 12 development-задач, 12 holdout-задач и 12 запросов доставки согласно разделу 5.5; карта проектов, типов задач, исходных SHA и применимых runtime-проверок. Задачи могут быть специально выбраны в реальном коде без текущего продуктового запроса.
- Проверка: задача имеет реальный инженерный смысл, ограниченный scope, проверяемый результат и не решена заранее в payload. Синтетически внесённые дефекты явно обозначены и не выдаются за обнаруженные реальные ошибки. Для каждой группы есть отрицательные случаи, где вмешательство не требуется.
- Принятие: есть разнообразие механизмов и не менее трёх задач-контролей в development; holdout не повторяет тот же дефект с переименованием. Проектная совместимость и право использовать исходники проверены. Нельзя заранее обещать конкретный исправляемый дефект в Countries/Firefox/Ghibli до его нахождения.
- При отклонении: заменять неподходящий проект/задачу до заморозки, сохраняя причину. Если нужен специалист для закрытого набора, представить пользователю ограниченное предложение; не создавать его автоматически.

**P2.2 — Определить oracle и процедуру принятия результата.**
- Результат: для каждой задачи — вход, обязательное поведение, недопустимые изменения, существенные дефекты, допустимые альтернативные решения, разрешённые проверки и grader. Review-задачи получают размеченные подтверждённые дефекты и чистые участки; implementation-задачи — проверяемый контракт поведения.
- Проверка: проверить oracle на правильном решении и минимум одном правдоподобном неправильном. Проверки должны ловить нарушение контракта, а не форму эталонного patch. Не включать оценочные ответы в материалы исполнителя.
- Принятие: решения можно оценить независимо от красноречия отчёта; спорные критерии разрешены до запуска. Недоказанное замечание не превращается в TP. Неполная разметка означает UNKNOWN для recall. Holdout-ответы недоступны автору улучшений; при невозможности такой изоляции статус проверки — development, а не независимый holdout.
- При отклонении: уточнить проверку до эксперимента. Не создавать тесты, повторяющие реализацию, ради числа PASS; test-writing требует покрывающего разрешения.

**P2.3 — Заморозить протокол и обеспечить независимость.**
- Результат: версия A, правила последующей фиксации C в P6.3, настройки модели, prompts, seeds/порядок если применимы, лимиты, одинаковые tools, правила остановки/исключения, журнал всех попыток и план анализа. Изолированные запуски допускаются только разрешённым способом.
- Проверка: спроектировать два проверочных сценария с заведомо разными payload; выполнить их в составе восьми delivery-попыток после P5 и подтвердить отсутствие утечки ответов/памяти. Порядок A/C сбалансирован и записан заранее. Проверить, что глобальные инструкции одинаковы, а различается только заявленный экспериментальный компонент.
- Принятие: P2-протокол фиксируется до оценки результатов C. Основная единица анализа — задача. Предлагаемый анализ: парные task-level доли успеха, таблица wins/ties/losses, интервалы с ресэмплингом задач с учётом проектных групп; метод и ограничения малого N записываются заранее. Ни число повторов, ни число проектов не маскируют зависимость наблюдений.
- При отклонении: загрязнённый run помечается и сохраняется; если затронута вся серия, серию не использовать для причинного вывода. Новый протокол получает новую версию, а не редактирует прошлый результат.

**P2.4 — Калибровать стоимость и утвердить конечный бюджет (завершение после P5).**
- До P3: согласовать ограниченный бюджет разработки и восьми delivery-попыток. После P5: выполнить эти восемь попыток и принять решение об основной серии. Предварительный C на этом шаге маркируется как development-версия; окончательный C замораживается P6.3.
- Результат: после восьми delivery-попыток — фактическое время, число действий, видимый расход/UNKNOWN, стоимость подготовки и прогноз диапазона для оставшихся 102 основных попыток. Отдельно учитывать grading, runtime и исправления.
- Проверка: заранее выбрать timeout и предел исправлений на попытку; провал/timeout остаётся провалом, а затраченное время входит в отчёт. Основную экономию нельзя считать только на удобном подмножестве успешных запусков. Публиковать capped time-to-acceptance для всех и дополнительный срез пар, где обе стороны успешны; согласовать трактовку цензурированных случаев до запусков.
- Принятие: пользователь выбирает размер программы, допустимую стоимость, численные пороги раздела 5.6 и предел коррекционных прогонов. Предлагаемый максимум — 110 основных + до 6 диагностических B, без автоматического запуска всего объёма. Для разработки — максимум две итерации изменения одной гипотезы; конкретный лимит повторных development-прогонов фиксируется здесь.
- При отклонении: уменьшить область заявляемой пользы или оставить результат предварительным. Не превращать 8 диагностических запусков в замену 12 независимых holdout-задач. Не оценивать процент недельного лимита из неизвестного числа токенов.

**Gate P2 до разработки:** протокол может опровергнуть гипотезу, бюджет разработки конечен, полномочия соответствуют действиям. **Gate P2.4 перед P6:** фактическая калибровка завершена, основной бюджет выбран. При недостаточной мощности допустим честный предварительный вывод вместо обещания доказательства.

### P3. Улучшить базу знаний

**P3.1 — Устранить противоречия и размножение норм.**
- Результат: точечные canonical patches с единым владельцем нормы, адресными ссылками и явными локальными исключениями. Исправленные зеркала только там, где они действительно используются.
- Проверка: producer/consumer-согласованность, входящие ссылки, bootstrap/route continuity, актуальные overrides. Проверить случаи новой задачи, продолжения после compaction и отсутствующего canonical checkout.
- Принятие: одинаковая задача получает одинаковое действующее правило; локальный документ не ослабляет более высокий authority; fallback честно сообщает ограничение. Миграция сохраняет уникальные знания и историю.
- При отклонении: откатить несовместимый маршрут либо исправить потребителей в одном ограниченном блоке. Не менять правила для получения удобного результата эксперимента.

**P3.2 — Сделать обязательный старт коротким и достаточным.**
- Результат: обязательное ядро требований и адресные ссылки на подробности; подробные recipes и исторические отчёты не читаются на каждой задаче. Никакая обязательная защита не исчезает без отдельного решения.
- Проверка: 12 диагностических запросов; сравнить фактически прочитанный обязательный контекст, число переходов и пропуски важных ограничений до/после. Проверить неоднозначный запрос и позднюю смену scope.
- Принятие: 12/12 правильно сохраняют обязательный authority; все заранее обязательные маршруты обнаружимы. Сокращение контекста засчитывается только при сохранённой полноте нужных требований. Остальная эффективность оценивается P6/P7.
- При отклонении: вернуть утраченное требование и пересмотреть разбиение; не добавлять общий «читать всё» как исправление одного промаха.

**P3.3 — Уточнить проектную память и передачу контекста.**
- Результат: минимальная память: identity, SHA/fingerprint, действующие решения, открытые риски, проверенные evidence, разрешения и следующий шаг. Отчёты и прошлые попытки остаются по ссылке.
- Проверка: продолжение после паузы, другая ветка, изменённый исходник, устаревшее разрешение, отменённая рекомендация. Read-only восстановление должно отличать факт от старого предположения.
- Принятие: ни один из пяти сценариев не наследует чужой ON, устаревший PASS, израсходованный grant или несуществующий next step. Компактные startup-файлы соответствуют действующему лимиту, длинный план не загружается автоматически целиком.
- При отклонении: ограничить запись до проверяемого факта и добавить точечную invalidation-причину. Не создавать вторую параллельную систему состояния.

**Gate P3:** KB стала однозначнее и адреснее; это ACCEPTED_STATIC/диагностическое evidence, пока не пройдены outcome-проверки.

### P4. Создать практическое содержимое Library

**P4.1 — Собрать доказательную основу выбранного модуля.**
- Результат: карта «инженерная ситуация → механизм ошибки → решение → пределы». Использовать реальные выбранные исходники, воспроизводимые минимальные примеры и первичные источники. Указать дату/версии и уверенность.
- Проверка: каждое значимое утверждение сверено с доступным первичным источником либо наблюдаемым поведением. Для изменяемых API/платформ — текущая официальная документация при наличии разрешённого доступа; недоступное знание не выдаётся за проверенное.
- Принятие: есть полезная конкретика сверх базовой нормы; обозначены случаи, когда совет неприменим. Ссылки на open source и заимствованный код имеют provenance и совместимые условия использования; не копировать проектную приватную информацию в reusable corpus.
- При отклонении: ограничить claim или не публиковать рецепт. Наращивание списка ссылок без синтеза не закрывает пункт.

**P4.2 — Оформить модуль для применения во время работы.**
- Результат: короткая входная карточка и детали по требованию: triggers/не-triggers; механизм; invariants; before/after; контрпример; диагностические признаки; проверка; trade-offs; версия; source; противопоказания.
- Проверка: Sol/medium на development-сценарии должен найти нужное действие без чтения всей Library; на негативном случае — объяснимо не применять рецепт. Пример должен показывать ownership, ordering, failure/cancellation и resource envelope там, где они существенны.
- Принятие: корректное действие и отказ воспроизводятся; код-пример проверен доступным способом, ограничения compile/runtime указаны. Непроверенный пример явно помечен и не предлагается как готовый production patch.
- При отклонении: исправить содержание либо trigger; не лечить неверный совет длинным предупреждением в конце. Удалить декоративные абстракции.

**P4.3 — Довести первый модуль сквозным проходом.**
- Результат: одна реальная задача от запроса до принятого результата с доказанной доставкой конкретного фрагмента и проверкой его корректного применения.
- Проверка: сопоставить trace, итоговый diff/замечания и контракт. Выделить факт использования, возможный причинный механизм и пока недоказанный сравнительный эффект. Runtime выполняется только в покрытом блоке.
- Принятие: нет критического разрыва «модуль существует, исполнитель его не получил / получил слишком поздно / применил неправильно»; один отрицательный сценарий также пройден. Это gate к масштабированию, не доказательство общей пользы.
- При отклонении: исправлять конкретный слой; максимум две development-итерации по одной гипотезе. При повторном отсутствии механизма пользы пересмотреть P1.2, не тиражировать формат.

**P4.4 — Расширить только проверенный формат.**
- Результат: оставшиеся 2–4 приоритетные темы по принятому контракту; реестр coverage и намеренно неподдержанных ситуаций. Повторяющиеся объективные проверки можно реализовать малым read-only инструментом вместо текста после сравнения стоимости.
- Проверка: для каждой темы минимум один полезный и один неприменимый сценарий; отсутствие конфликтов между модулями; разумная композиция на задаче с двумя темами. Проверить, что инструмент на чистом примере не выдаёт ложный блокер и не модифицирует source.
- Принятие: каждый модуль соответствует P4.1/P4.2; более сложный инструмент имеет наблюдаемое преимущество над инструкцией. Количество тем само по себе не закрывает gate.
- При отклонении: исключить слабую тему из релиза, сохранив причины; не расширять ради полного оглавления iOS. Создание новых tools/MCP/установок по-прежнему требует отдельного решения.

**Gate P4:** выпускаемый материал достоверен и применим, а его отсутствие/неприменимость распознаётся. Общая outcome-польза ещё требует P6/P7.

### P5. Обеспечить своевременную доставку знаний

**P5.1 — Реализовать минимальный маршрут выбора.**
- Результат: вход задачи → признаки/риски → нужный стандарт + нужный практический модуль → достаточный контекст. Неоднозначность ведёт к точечному уточнению либо ограниченному чтению.
- Проверка: 12 запросов, включая четыре негативных/неоднозначных/устаревших; вход из нового чата и восстановленного task state. Отдельно случаи «Library не нужна» и «нет подходящего знания».
- Принятие: обязательные правила не пропущены; нужный материал доставлен до соответствующего решения; нет ошибочной активации на негативных случаях. Число открытых документов и overhead записаны, допустимый предел заранее фиксируется P2.
- При отклонении: уточнить trigger или индекс. Переход к полнотекстовому/семантическому поиску возможен только после измеренного ограничения простой маршрутизации и решения P1.2.

**P5.2 — Проверить границы контекста и сбои доставки.**
- Результат: поведение при отсутствующем документе, устаревшем SHA, неверном project selector, смене scope, обрыве/compaction, выключенном экспериментальном слое.
- Проверка: контролируемые read-only сценарии с сохранённым исходным состоянием; источник данных не получает authority инструкций. Проверить, что отсутствие optional Library не мешает безопасно работать с базовой системой.
- Принятие: нет silent success, чужого режима, потери пользовательского ограничения или бесконечного повторного чтения. Необходимая недоступная норма даёт BLOCKED, optional материал — явное ограничение и допустимый fallback.
- При отклонении: исправить конкретную ветвь; не ослаблять канонический bootstrap ради успешного старта.

**P5.3 — Добавить достаточную наблюдаемость без новой бюрократии.**
- Результат: в существующем task receipt фиксируются версии прочитанного, момент доставки, использованный механизм и фактический outcome; tokens/usage только при доступных данных.
- Проверка: независимое чтение артефактов позволяет отличить NOT_READ, READ_NOT_APPLIED, APPLIED_CORRECTLY, APPLIED_INCORRECTLY и NOT_APPLICABLE. Самоотчёт сопоставляется с trace и diff.
- Принятие: запись помогает объяснить исход без повторного запуска; объём журналирования ограничен P2 и не требует новой постоянной службы. Секреты и ненужные пользовательские данные не попадают в evidence.
- При отклонении: UNKNOWN предпочтительнее выдуманной точности. Удалить поля, которые не используются в решениях.

**Gate P5:** допускается development-сравнение. Неудача доставки остаётся неудачей C; её нельзя исключить как «не совсем Library».

### P6. Проверить на development и заморозить кандидата

**P6.1 — Выполнить 24 основные development-попытки.**
- Результат: A/C на 12 задачах с одинаковыми условиями и полным журналом. Implementation/review оцениваются по своим заранее зафиксированным контрактам.
- Проверка: соблюдение модели, source SHA, бюджета, независимости; фактические builds/tests, если они нужны и разрешены; отсутствие посторонних source-изменений.
- Принятие: серия валидна даже при отрицательном результате; все попытки оценены, причины провалов разобраны. «Серия выполнена» отдельно от «кандидат улучшен».
- При отклонении: протокольную ошибку исправить по заранее заданной процедуре; не повторять проигрышную попытку молча. Изменение задачи после просмотра результата аннулирует её сравнительный статус.

**P6.2 — Исправить подтверждённые ограничения, проверить вклад.**
- Результат: максимум две итерации на гипотезу в бюджете P2; каждое изменение связано с наблюдаемой причиной. До шести B-прогонов только если это помогает выбрать между KB, модулем и доставкой.
- Проверка: исправление закрывает исходный failure, не ухудшает связанный негативный случай и не вшивает ответ development-задачи. Если разница обусловлена просто более длинным prompt или дополнительным временем, это отражено как часть стоимости системы.
- Принятие: нет известных неустранённых P0–P2 в кандидате; выбранная конфигурация лучше объясняет наблюдения и имеет шанс выполнить P7. Отсутствие самостоятельного плюса Library не блокирует полезную перестройку всей связки.
- При отклонении: упростить/удалить мешающий элемент либо REJECTED/INCONCLUSIVE. Третья итерация — отдельное решение с новым основанием, а не автоматическое продолжение.

**P6.3 — Заморозить C для независимой проверки.**
- Результат: immutable manifest C, окончательная таблица различий A/C, checklist готовности, остаточные риски и точная очередь holdout.
- Проверка: полный semantic diff-review против контракта; маршруты/зеркальные claims/потребители; отсутствие ответов holdout в payload; достаточные разрешения и бюджет следующего блока.
- Принятие: кандидат не меняется во время holdout. Любое исправление затем создаёт C2 и отдельный протокол; результаты C1 сохраняются. Условия Q/E и статистического вывода уже зафиксированы.
- При отклонении: holdout не запускать. Закрыть конкретный blocker, не расширяя содержание.

**Gate P6:** готов проверяемый кандидат, а не заранее «успешная Library».

### P7. Измерить независимый результат

**P7.1 — Выполнить 72 holdout-попытки.**
- Результат: 12 новых задач × A/C × 3 повтора на Sol/medium. Исполнители не получают ответы других попыток; разработчик C не использует holdout для исправления в ходе серии.
- Проверка: автоматические доступные объективные checks + semantic adjudication; порядок, версии, timeout, недостающие данные и нарушения протокола видимы. Повторы нужны для устойчивости, а не для выбора лучшего ответа.
- Принятие: все валидные попытки входят в анализ; неполный запуск даёт неполную серию. Досрочная остановка допустима по безопасности/бюджету с соответствующим статусом, но не по первым положительным результатам.
- При отклонении: остановить небезопасный путь и сохранить evidence. Число запланированных попыток не оправдывает продолжение при системном нарушении полномочий.

**P7.2 — Провести слепую по возможности оценку и анализ.**
- Результат: результаты каждой задачи/проекта/типа, Q/E, confidence/uncertainty, FP, регрессии, время, переделки, контекст, maintenance; спорные оценки отдельно.
- Проверка: сверить фактический diff/выводы с oracle; reviewer не узнаёт A/C до выставления оценки, насколько это возможно. Автоматические метрики не отменяют semantic-review. При отсутствии независимого оценщика прямо указать ограничение, не называть self-review независимым.
- Принятие: ACCEPTED_SCOPED только при выполнении всех обязательных gates и одного заранее выбранного допустимого пути Q/E; область результата соответствует выборке. Субъективная полезность комментариев не заменяет outcome. Недостаточная уверенность — INCONCLUSIVE.
- При отклонении: отрицательный результат не переименовывать в успех внедрения. Назвать слой и предел доказательств; сохранить полезные безопасные исправления отдельно от claims об эффективности.

**P7.3 — Принять решение по системе и её частям.**
- Результат: таблица «оставить / упростить / ограничить область / удалить / исследовать позже» с evidence по каждому компоненту; сравнение benefits/costs и рекомендация пользователю.
- Проверка: решение согласуется со всеми исходами, включая проигрыши, стоимость подготовки и нагрузку поддержки. Нет выбора только выигравшего проекта задним числом для общей победы.
- Принятие: пользователь принимает значимый rollout/trade-off. Возможные итоги: scoped adoption; дополнительная ограниченная проверка с новым набором; экспериментальный статус; отказ от неэффективной части. Все являются честными результатами, но только первый с выполненными gates позволяет заявить подтверждённое улучшение в указанной области.
- При отклонении: не делать Library обязательной ради закрытия плана. Новая серия требует новой гипотезы, бюджета и неиспользованных задач.

**Gate P7:** имеются доказательства и решение, соразмерные данным. План не требует получить положительный результат любой ценой.

### P8. Внедрить принятый вариант и сохранить результат

**P8.1 — Проверить перенос в обычный рабочий процесс.**
- Результат: три свежие прикладные задачи, по одной на проект, A/C по одному запуску (6 попыток); обычные task inputs без лабораторных подсказок. Если проект заменён в P2, использовать принятую тройку.
- Проверка: новая/возобновлённая задача действительно получает C, соблюдает ограничения и доходит до принятого результата. Применимые iPhone runtime-проверки — согласно матрице P2; не требовать deployment на физический девайс.
- Принятие: C решает все три задачи без подтверждённой существенной системной регрессии; результат не переопределяет основной статистический вывод P7. Это проверка переносимости, а не самостоятельное доказательство массовой пользы.
- При отклонении: ограничить adoption затронутого сценария, установить причину. Изменённый C требует релевантной повторной проверки и честного ограничения прежнего evidence, без бесконечного полного перезапуска.

**P8.2 — Опубликовать канонические изменения и проверить потребителей.**
- Результат: reviewed commits canonical docs и отдельно разрешённых repositories; актуальные manifest/links; task-local mirrors; финальные SHA и exact-HEAD receipts.
- Проверка: полный final-diff semantic-review; relevant static gates; после commit exact HEAD review, отсутствие новых изменений перед push, подтверждение remote SHA. Проверить реальные пользовательские checkout и branch/worktree occupancy, а не только граф коммитов.
- Принятие: опубликованы именно принятые изменения; чужие данные сохранены; временные результаты не добавлены массово в Git. Если прежнее разрешение на main/development действует для затронутого repo, обе ветки содержат нужную историю и доступны пользователю. Занятую main в сервисном worktree повторно не закреплять.
- При отклонении: остановить push при P0–P2 или неясной принадлежности файлов. Не использовать force/reset/clean для искусственно чистого статуса. Незакоммиченные чужие данные явно указать, а не заявлять общий clean.

**P8.3 — Проверить восстановление и обратимость.**
- Результат: точные версии предыдущего/нового payload, совместимый путь отключения optional части и инструкция восстановления состояния без утраты пользовательской работы.
- Проверка: в разрешённой изоляции либо read-only реконструкцией проверить путь rollback, ссылки, конечный Library mode и совместимость project memory. Не переключать пользовательские проекты ради демонстрации без покрывающего разрешения.
- Принятие: понятно, что и как восстановить; объявлять rollback «проверенным исполнением» можно только после фактического выполнения. Документированная read-only проверка маркируется своим уровнем уверенности.
- При отклонении: не расширять rollout. Устранить зависимость, делающую optional компонент фактически обязательным.

**Gate P8:** результат доступен в реальном workflow, опубликован и обратим; число коммитов не является мерой улучшения.

### P9. Сделать качество устойчивым и закрыть цикл

**P9.1 — Установить лёгкий жизненный цикл знаний.**
- Результат: у активного модуля owner-role, scope, version, источник, дата последней проверки, события invalidation и признаки устаревания. События: изменение платформы/зависимости, контрактов проекта, повторный false positive, изменение модели/маршрута, новый подтверждённый failure.
- Проверка: взять устаревший рецепт и проследить, как он перестаёт предлагаться как проверенный, кто принимает решение и какие ограниченные проверки нужны. Не запускать полный benchmark при орфографической правке.
- Принятие: знание может быть исправлено, ограничено или выведено из использования без массового чтения всего корпуса. Нет фоновых задач/автоматизаций, созданных без разрешения.
- При отклонении: упростить lifecycle до существующих task receipts; не создавать отдельный продукт управления знаниями.

**P9.2 — Зафиксировать результат, ограничения и стоимость владения.**
- Результат: итоговый scorecard A/C, принятые/отклонённые компоненты, объём доказанной применимости, затраты разработки/эксперимента/поддержки, UNKNOWN и оставшиеся риски; backlog только с обоснованием ценности.
- Проверка: каждое сильное утверждение имеет ссылку на outcome evidence; исключённые пользователем проверки не значатся долгом. Старые экспериментальные выводы не переписываются. Оценка окупаемости условна: частота будущих задач неизвестна.
- Принятие: пользователь может понять, что стало лучше, где это доказано, чего не известно и сколько стоит продолжение. Отсутствие пользы отдельного слоя не скрыто за общим количеством выполненных пунктов.
- При отклонении: ослабить claim до подтверждённого уровня; не заменять недостающие измерения обещанием будущей пользы.

**P9.3 — Закрыть либо явно остановить программу.**
- Результат: компактные plan/handoff со статусами всех пунктов; canonical publication; один next step или отсутствие дальнейшей работы. Неиспользованные разрешения и открытые пользовательские решения перечислены.
- Проверка: R1–R10 покрыты доказательствами либо явно не достигнуты; нет забытых P0–P2, скрытого обязательного follow-up, незапушенных собственных полезных изменений в согласованном Git scope. Проверить отсутствие созданных по пути неучтённых сервисов/агентов/автоматизаций.
- Принятие: различать «программа завершена», «улучшение подтверждено в scope» и «эксперимент остановлен без доказательства». Для последнего требуется понятное решение пользователя; нельзя отметить R1 выполненным только потому, что все документы написаны.
- При отклонении: указать единственный реальный blocker и ограниченное действие. Не оставлять бесконечный список обязательных новых пилотов.

**Gate P9:** цикл закрывается честным итогом и поддерживаемым состоянием.
## 7. Контрольные точки, доказательства и оценка масштаба

### 7.1 Последовательность решений

| Точка | Что предъявляет исполнитель | Решение / действие |
|---|---|---|
| Принятие плана | Цель, этапы, границы, оценки UNKNOWN, схема эксперимента | Пользователь принимает/корректирует программу; конкретные runtime/agent права не предполагаются |
| После P0 | Baseline, подтверждённые проблемы, permissions | Продолжить разрешённую диагностику; уточнить только действительно недостающие полномочия |
| P1.2 | Конкретное сравнение подходов с влиянием на работу | Выбор значимой архитектуры пользователем |
| P2 / возврат P2.4 после P5 | Набор задач, oracle, протокол; затем прогноз после калибровки | Сначала бюджет разработки, затем основной серии; критерии, изоляция и полномочия до соответствующих запусков |
| После первого модуля P4.3 | Сквозной полезный/негативный сценарий, фактическая стоимость | Масштабировать принятый формат или исправить один выявленный разрыв |
| P6.3 | Frozen C, development results, остатки | Запустить только разрешённую holdout-серию либо остановиться |
| P7.3 | Полный scorecard и значимые проигрыши | Принять scoped rollout / ограничить / оставить экспериментальным / отказаться |
| P9 | Evidence, опубликованные версии, ограничения | Закрыть цикл с точным статусом результата |

Это не требование задавать вопрос после каждого пункта. Внутри уже принятого scope исполнитель действует сам. Checkpoint нужен для выбора значимого подхода, нового разрешения, увеличения бюджета или изменения заявляемого результата.

### 7.2 Что считается достаточной проверкой

| Изменение / утверждение | Минимально релевантное evidence | Чего это не доказывает |
|---|---|---|
| Ссылка, индекс, зеркало | Разрешение ссылок, версия, точное сравнение, relevant docs checker | Улучшение качества инженерного решения |
| Норма или её перенос | Semantic-review authority и всех затронутых потребителей; сценарии конфликтов | Отсутствие всех будущих конфликтов |
| Router / контекст | Позитивные, негативные, неоднозначные и failure cases; trace | Пользу полученного знания |
| Рецепт / пример кода | Проверка контракта и контрпримера; compile/runtime где это необходимо | Универсальность за пределами заявленных версий и условий |
| Изменение поведения приложения | Контракт, affected-call-sites review, targeted regression; применимый разрешённый runtime | Качество всей KB/Library |
| Claim об эффективности системы | Валидные A/C outcomes, повторения, независимые задачи, стоимость и неопределённость | Глобальный оптимум и пользу на всех будущих проектах |
| Публикация | Final diff, exact-HEAD receipt, remote SHA, реальные checkout | Правильность поведения без предыдущих semantic gates |

Build/tests не назначаются всему этапу одинаково. Матрица задачи указывает цель каждой проверки, окружение, ожидаемый сигнал, основание полномочия и результат. Неприменимость имеет причину. Уже действующее неизменённое evidence используется повторно; расширение проверок связано с новым риском.

### 7.3 Честная оценка ресурсов

До P0–P2 нельзя надёжно обещать календарное время и расход токенов. Это многoэтапная программа, а не ещё один короткий review. Расход состоит из подготовки/очистки знаний, реализации, 110 основных попыток, оценки результатов, необходимых сборок и поддержки. Каждый компонент учитывается отдельно.

После готовности P5 пункт P2.4 калибрует диапазон по восьми коротким попыткам. Они оценивают overhead доставки, но могут недооценивать полноценные implementation-задачи; прогноз корректируется по первым заранее выбранным development-парам без изменения критериев успеха. Перед большим запуском исполнитель показывает диапазон, допущения и резерв. Если пользовательский weekly budget недоступен, состояние UNKNOWN явно сохраняется.

Доступны три размера решения, выбираемые **до** основной проверки:

- **Полная программа этого плана:** 12 development + 12 holdout задач, три повтора holdout, перенос на трёх проектах. Даёт наиболее содержательный из предложенных выводов, но не гарантирует статистически определённый результат.
- **Ограниченный цикл:** один модуль, меньше проектов/задач, доставка и development. Подходит для выявления дефектов дизайна; общая эффективность остаётся непроверенной. Количественные критерии полного плана не переносятся на него.
- **Точечное исправление:** устранить подтверждённую противоречивую норму/ошибку маршрута, проверить её потребителей и остановиться. Полезное исправление возможно без заявления об эффективности системы в целом.

Рекомендация: принять полную структуру, исполнять её по gates, окончательный размер дорогой серии выбрать после калибровки. Не выделять заранее неограниченный ресурс ради формулировки «максимально».

## 8. Проверки отхода от цели и правила остановки

### 8.1 Перед каждым блоком

Исполнитель отвечает в компактном контракте:

1. Какое требование R1–R10 и какой наблюдавшийся дефицит затронуты?
2. Какое конкретное решение Sol/medium станет правильнее, быстрее или устойчивее?
3. Какой наблюдаемый результат опровергнет нашу гипотезу?
4. Может ли меньшая правка дать тот же эффект?
5. Доступны ли входные данные, разрешение и бюджет? Не используется ли испорченный holdout?
6. Какой итог позволит остановиться, и что останется UNKNOWN?

Если на 1–3 нет содержательного ответа, implementation не начинается. Нельзя заменять ответ фразами «повысит качество», «улучшит полноту», «полезно на будущее».

### 8.2 После каждого блока

Сопоставить ожидание и факт: исправлен ли конкретный failure; изменился ли task outcome; какие отрицательные случаи проверены; сколько добавлено обязательного чтения/действий; появились ли новые пользователи/потребители или обязательства поддержки. Отдельно отметить возможный перенос сложности из Library в KB — он не считается бесплатным.

| Признак отхода | Проверка | Обязательное действие |
|---|---|---|
| Растёт corpus, outcomes не улучшаются | Каждое дополнение имеет evidence и потребителя? | Приостановить расширение, проверить доставку/исполнение/лишний контекст |
| Повторяются похожие пилоты | Новый запуск проверяет новую заранее сформулированную гипотезу? | Без новой гипотезы не запускать |
| Подгонка под benchmark | Советы содержат имена/ответы конкретной задачи вместо механизма? | Убрать leakage; загрязнённый holdout перевести в development |
| Выбраны только удобные результаты | Полный журнал сходится с числом запланированных попыток? | Восстановить все исходы; остановить сильный claim |
| «Прочитал» используется как «помогло» | Есть изменение правильного outcome и сравнительные данные? | Разделить delivery evidence и outcome evidence |
| Больше отчётов, чем полезной диагностики | Кто использует каждое поле/артефакт для решения? | Удалить лишнее; сохранить минимальную воспроизводимость |
| Строится новый framework/поиск/MCP | Простое решение измеренно недостаточно? | Вернуться к P1.2 и получить выбор/разрешение |
| Качество ухудшено ради скорости | Существенные дефекты, FP, пропуски или ослабление checks? | Заблокировать adoption и исправить либо отклонить вариант |
| Исследование стало развитием приложения | Правка необходима для проверяемого системного механизма? | Вынести лишнее в отдельный scope, не реализовывать молча |
| Смена модели маскирует слабость системы | A/C остались Sol6.1/medium? | Отдельная серия; не смешивать результаты |
| Разрешение расширено предположением | Есть действующая точная пользовательская authority? | Остановить только зависимое действие |
| Бесконечная доработка | Исчерпаны две итерации гипотезы/бюджет? | Предъявить результат и ограниченный выбор; не продолжать автоматически |

### 8.3 Жёсткие остановки

Нарушение полномочий, риск потери чужой работы, подтверждённая существенная регрессия в публикуемой системе, загрязнение основного сравнения, невозможность проверить обязательный контракт, превышение принятого бюджета или повторение без новой информации останавливают соответствующий блок.

При P0–P2 в изменении — исправление либо явное пользовательское исключение по действующим правилам, а не молчаливый merge. Если blocker — только недоказанность общей эффективности, безопасные отдельные исправления могут сохраняться с ограниченным claim, но система не объявляется доказанно улучшенной.

После остановки предъявить: выполненное, конкретный риск, причину неэкономичности продолжения, три ограниченных варианта — одно необходимое исправление; сокращение scope/экспериментальный статус; новый отдельно оценённый цикл. Не перекладывать на пользователя самостоятельный разбор большого лога.

## 9. Артефакты, шаблоны и трассировка

Не создавать каждый файл заранее. Достаточно существующего task storage и документов/JSON по мере появления данных. Реестр показывает путь, версию и актуальный статус; сырые logs не входят в обязательный startup.

| Артефакт | Когда | Содержание |
|---|---|---|
| `plan.md`, `handoff.md` | Старт и смысловые границы | Короткое состояние, следующий шаг, authority, ссылки |
| Baseline/permissions record | P0 | Roots/SHA, grants, drift, реальные проблемы |
| Design decision | P1 | Варианты, trade-offs, выбор пользователя, границы слоёв |
| Evaluation protocol + case registry | P2 | Задачи, oracle, изоляция, метрики, бюджеты, порядок, exclusions |
| Module records | P4 | Версия, provenance, механизм, примеры, ограничения, проверки |
| Attempt ledger + evidence | P5–P8 | Все попытки, включая failures; artifact hashes, outcome, затраты |
| Final scorecard + publication receipts | P7–P9 | Парные результаты, uncertainty, решения, Git SHA, ограничения |

**Карточка изменения:** ID; R-ID; подтверждённая проблема/гипотеза; authority; исходные версии; ожидаемое поведение; затронутые consumers; state/time/resource/failure invariants; patch scope; проверки; критерий остановки; фактический итог.

**Карточка задачи:** case ID; проект/версия; development/holdout; реальная/синтетическая; тип и сложность; одинаковый input A/C; ожидаемые invariants; oracle; допустимые альтернативы; запреты; checks; timeout; источник разметки; provenance; статус независимости.

**Карточка попытки:** case/arm/repeat; модель/reasoning; payload/source SHA; start/end; порядок; tools/permissions; фактическая доставка; outputs; checks; TP/FP/UNKNOWN или success/failure; переделки; время/usage/UNKNOWN; протокольные отклонения; решение grader; ссылки на evidence.

**Карточка модуля:** проблема; trigger/не-trigger; механизм; invariants; краткий рецепт; правильный и неправильный пример; диагностический сигнал; применимые проверки; trade-offs; версии/источники; подтверждённость; дата/событие revalidation; связь с canonical нормой.

**Итог этапа:** ID/status; что изменилось; доказательства; принятые критерии; непрошедшие критерии; расход; drift-check; residual risk; один next step. Слова «полностью», «безопасно», «оптимизировано» требуют соответствующего объёма evidence.

## 10. Риски и работа с неизвестным

| Риск | Ранний сигнал | Мера |
|---|---|---|
| Новые материалы повторяют знания модели/KB | Нет изменения решений, больше чтения | Сократить общие правила, проверить конкретику, допускается перенос/удаление Library-компонента |
| Доставка не работает | NOT_READ, позднее чтение, timeout | P5; такой исход учитывается в C, не скрывается |
| Улучшение только на известных примерах | Development выиграл, holdout нет | Независимый набор и запрет доработки по holdout |
| Самооценка завышает пользу | Красивый report без подтверждённого результата | Oracle, blind grading где возможно, evidence, прозрачные ограничения независимости |
| Малый N и нестабильность модели | Большой разброс повторов/интервалов | INCONCLUSIVE; новая серия только отдельным решением |
| Проект несовместим с runtime matrix | Deployment/dependencies не позволяют запуск | Проверка P2; замена задачи до freeze или обоснованное N/A, без установок по умолчанию |
| Польза съедена сопровождением | Слишком много зеркал/обязательных шагов | Один owner на норму, минимальная память, учёт maintenance |
| Программа бесконечно растёт | Новая тема после каждого review | 3–5 тем, gates, две итерации на гипотезу, конечный бюджет |
| Улучшение не переносится на обычную работу | Успех только с лабораторными подсказками | P8.1 и ограничение claims |
| Изменился canonical/model во время серии | Разные rules/version между A/C | Общая версия/пауза/новый протокол; не замораживать отменённые пользовательские ограничения |

Тематическое покрытие первого цикла ограничено выбранными 3–5 механизмами. Архитектура, безопасность, доступность, сеть, UI, локализация, сборка, миграции и другие области не обязаны получить новый модуль каждая. Действующие базовые нормы сохраняются.
