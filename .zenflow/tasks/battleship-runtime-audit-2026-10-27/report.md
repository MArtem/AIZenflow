## Failures and limitations

Initial sandboxed Simulator/Instruments discovery failed due system access; retry with explicitly authorized escalation succeeded. First Time Profiler attach failed because the test's process ended; retry attached to confirmed PID. First scroll performance build failed because `XCTHitchMetric` requires iOS 26; test now uses an availability guard and was rebuilt successfully on iOS 27. Preserve all failed logs.

During the later Game Performance Overview follow-up, `simctl list devices booted` intermittently reported the iOS 27 device as Booted, while subsequent `xctrace` calls reported a disconnected/unloaded CoreSimulatorService and no matching device. A new Time Profiler recording therefore did not start, and no app test was launched for that attempt. This is an environment/tooling interruption, not an application failure. No service restart or tool installation was attempted.

No before/after baseline or approved app performance budget exists. Debug/XCUITest timings and Simulator measurements do not establish physical-device, real-user or comprehensive production performance. Memory retention/long-session slope, background/foreground during battle and interruption states, localization beyond English, and broad accessibility behavior remain unverified. Both player-win and computer-win UI outcomes now pass with retained terminal labels and reset, but their full endgame paths do not have per-turn timing profiles. `XCTHitchMetric` remains unmeasured despite passing tests. A 500-query state-neutral control independently produced the same +409.6 kB memory delta as the 20-shot run, so the previous memory-growth observation cannot be attributed to changed game state; neither result identifies an allocation owner or proves a leak. The first fresh-shot attempt was blocked when CoreSimulator temporarily lost the requested destination; after recovery, later runs passed. An intermediate test-only failure assumed an exact "Your turn" status and rejected the normal "Computer missed. Your turn." result; the assertion was broadened to match the expected turn suffix. This was a harness expectation error, not an observed app defect. A four-shot test captured only Miss, then a 20-shot run retained outcomes: 6 Hit and 14 Miss; no Sunk was observed. Native network, backend and durable user data are not observed in the reviewed app, but no whole-target security certification is claimed. iPad, physical-device and actual VoiceOver checks OMITTED_BY_USER, never PASS. Firefox, Share and Library holdout were not activated.

No independent review or full-app release-readiness claim. Source/code hypotheses and actual observations are separate; unrun scenarios are not counted as successful. No changes to app code, project/scheme, signing, CI or Git were made.

The latest profiling-system iteration changed only UI-test metric declarations to include app-targeted CPU in bounded intervals. A standalone XCTest API type-check passed; neither full target compilation nor runtime collection of those CPU values passed. Xcode reported denied access when opening its CoreSimulator log under `~/Library/Logs`; CoreSimulatorService and simdiskimaged were also unavailable. A first standalone `swiftc` invocation attempted its default module cache under `/Users/Artem/.cache/clang` and was denied before writing; retry used a task-local module cache. DerivedData, logs and compiler outputs remained inside `.zenflow`. No external cache or service was repaired or modified.

The built-in Game Performance Overview template was also tried during a Release scroll scenario. Its active-scroll trace did not produce per-frame rows for BattleshipGame; the all-process CPU table contained only nine app samples. Treat both frame pacing and a useful scroll CPU profile as NOT_MEASURED rather than interpreting empty/sparse tables as evidence of smooth performance.

Static review identified one narrow follow-up for the hit/sunk workload: `computerBoard` is observable state with no UI consumer, while every view observes the same `BattleshipGame` object. Its mutations could cause redundant view invalidation, but SwiftUI coalescing may eliminate the cost; this remains a measurement hypothesis. A useful follow-up requires a paired hit/sunk workload with sufficient app-specific CPU/update evidence before changing the publisher contract.

## Review findings and scope

No confirmed P0–P2 app defect was established within the exercised scenarios. The repeated microhangs in `shooting-hangs.xml` are an observed diagnostic signal with an automation-related alternative, not an attributed app defect. A priority assessment cannot be assigned confidently without a comparable control. Existing product requirements are not complete enough to infer all expected behavior. Player-win and computer-win UI outcomes are now confirmed; only the player win was captured in the earlier endgame run and the opposing outcome in a separate Release run. Unmeasured areas include cold-cache, warm and first-interactive launch time, per-turn endgame profiles, independent hitch and long-term memory retention, full long-session behavior, error/accessibility configurations and full production/release gates. Selected UI passes do not establish absence of unobserved defects.
