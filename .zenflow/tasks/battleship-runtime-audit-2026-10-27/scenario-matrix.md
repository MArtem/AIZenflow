# BattleshipGame: runtime scope and evidence matrix

Target: game screen and model on iPhone Simulator. Use actual interactions as workloads, with recorded build, OS, target PID, driver and interval. PASS below is functional only; no production or hardware claim. Existing evidence is in `report.md`. A missing diagnostic is NOT_MEASURED; excluded checks are OMITTED_BY_USER.

| 1 | Fire hit/miss, duplicate shot, sinking | Main-thread work/hangs, UI updates, CPU, allocation and responsiveness | Original Debug trace has 15 microhangs. Paired 15-tap controls over five cells show no hangs during either tap loop; random fleet and driver differ from each other and from original workload. One 573 ms placement hang did not recur in one Debug repeat; one Release control also had no >250 ms hangs. App-attached paired controls with the same 15 taps showed ~7.57 s / 1,471 app samples (1,052 Main Thread) for precomputed coordinate taps and ~7.18 s / 2,618 samples (2,121 Main Thread) when querying each cell by label. Approximate alignment and random fleet differences limit causality, but accessibility query servicing is a concrete profiling confound. A 20-shot Release iOS 27 sweep captured 6 Hit and 14 Miss outcomes (no Sunk); nineteen timed samples averaged 0.422916 s and physical-memory differences averaged 82.782 kB. App-attached Time Profiler covered all 20 taps: 15,024 app samples (12,840 Main Thread), only 35 app-binary frames, one `fire(at:)` sample; no app potential-hang rows >250 ms. This does not rule out short CPU bursts or frame hitches. In another profiled repeat, clock mean was 0.430 s and absolute physical memory rose 557.056 kB; do not compare as a performance regression because run/instrumentation and stochastic fleet differed. App-targeted XCTest CPU metrics have been added to existing bounded shot/query intervals, but the latest collection attempt did not reach tests, so those values remain NOT_MEASURED. Query-only memory growth is also confounded; there is no leak attribution. Static follow-up: `computerBoard` is published but has no UI consumer; redundant invalidation during hit/sunk is possible but unmeasured. The model processes turns synchronously on `@MainActor` and scans a fixed maximum of 100 cells; each of the 200 rendered cells computes an accessibility label. This makes XCTest snapshot overhead plausible, not a confirmed UI bottleneck. |

| 2 | Play to win and loss, reset, play again | State transitions, retained memory after repeated cycles, CPU and UI update behavior | Player win and reset passed on iOS 27 with outcome `You sank the Carrier and won!`. Attachment started ~19 s after shooting began, so early shots are not covered. A separate Release iOS 27 run retained `You sank the Submarine! Computer won. Try again.` and passed reset; full run 174.472 s. Separate New game tap clock samples 0.440636, 0.433641 and 0.431754 s, peak physical memory 43,370.920–43,387.304 kB and per-iteration difference 49.152 kB. XCUITest/Simulator overhead apply; this profile is not a frame-pacing, real-user latency or leak verdict. Long-session memory and per-turn isolated profiles remain unverified. |
